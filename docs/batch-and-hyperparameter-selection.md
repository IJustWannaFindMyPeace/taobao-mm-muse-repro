# 批大小与超参数选择：扩容前必做检查

batch=32 是已验证稳定且用于现有受控对照的起点，不是通过批大小搜索得到的最优值，也不是已确认的显存上限。当前四组基线保持该协议以完成同口径对照；不在运行中更改参数。扩大数据规模或追加全套多种子前，须先执行本检查。

## 资源筛选

在固定 5% 数据、L=1000、相同初始化与采样规则下，以代表性 C6、R4 和 ID 检索模型串行探测 batch 32/64/128/256；满足资源余量且吞吐仍有改善时再试 512/1024，达到阈值或收益饱和即停止。各候选需覆盖热身后的相近曝光量，并保证足够测量时间，不能只用同样 100 步的耗时直接比较。记录曝光/秒、分配及保留显存、进程内存、系统可用内存、数据读取与计算开销。单次 CUDA OOM 后进程退出，清理资源再进行下一独立试验。

扩大 batch 主要增加批次相关的梯度、激活与数据传输；当前约 7.72 GiB 的 embedding 和 Adam 状态不会按 batch 成比例增长。故当前约 7.8 GiB 峰值不能证明 batch 64 或 128 放不下；也不能据此保证 1024 可行。小 batch 可能导致较多优化器更新及较低设备利用率，需要实测。

## 训练质量筛选

资源筛选保留 2–3 个可行候选，再在固定数据规模上检查验证 AUC/GAUC/LogLoss、损失曲线、更新次数和端到端时间。embedding 与 dense 学习率分别评估，不盲目按 batch 倍率线性放大；现有均为 0.001，而论文与参考源码配置不同，必须明确记录。

一轮训练包含相同曝光数量，但不同 batch 对应不同更新次数：3,052,475 条数据在 batch 32 下约 95,390 次，在 1024 下约 2,981 次。因此同为一轮并非相同优化过程。先以相同曝光预算和一轮协议评估，必要时另设更新次数匹配的诊断表，不能将两种预算混写。

梯度累积作为可选工程方案，需正确按实际样本数归一化、处理末批、核验 sparse 梯度与更新时机。它可以改变有效 batch，但不自动改善吞吐，也不省去 embedding/优化器状态；不能把多次 optimizer.step 的小批量训练叫作大 batch 等价训练。

## 决策与结果保留

按可接受的验证质量、稳定性、吞吐与整套预算选择共同主配置，而不是追求最大 batch 或最大数据规模。数据规模、batch、学习率、epoch 及优化器协议统一评估和冻结；主表各方法原则上使用共同预算。若需要模型特定调参，使用相同验证调参预算并单列。

已完成的 batch=32 结果保留为既定协议下的验证证据。新协议需要统一重跑核心对照，不与旧协议结果直接混成单变量结论。保留测试集不得用于超参数或数据规模选择。当前没有执行本批大小扫描，不能以本文件冒充选择结果。
