# 阶段 10：固定曝光预算的批大小资源扫描

## 当前状态

seed 42 的四组适配基线已完成全轮训练，资源检查未触发停止，检查点重载误差为零；保存预测的独立逐行审计和配对效果分析尚未完成。随后启动批大小资源扫描，不与训练或重型预测审计并发。尚未选定新 batch 或最终数据规模。

## 扫描设计

代表模型为 C6（历史 200，冻结同一预训练内容分支，使用经摘要校验的 SimTier 缓存）、R4（历史 1000）和商品+类目 ID 检索模型（历史 1000）。各模型内比较 batch 32/64/128/256，K=50、ID 维度 16、优化器及学习率与现有协议一致。C6 与 R4 采用各自实际主协议长度，不把跨模型吞吐差异归因于模型结构本身。

每次独立进程、相同 seed 42 初始化与训练曝光顺序，先热身 4,096 条，再测量相同的 65,536 条曝光。输入行序摘要写入报告。测量期不足 30 秒时标记，进入候选复测时扩大共同测量预算；不将不同 batch 的同样步数耗时直接比较。

输出曝光/秒、数据查表/传输/计算更新耗时、PyTorch 分配与保留显存、按步采样的进程 RSS 与系统可用内存。同步计时包含测量开销，单次顺序扫描会受缓存影响；可行候选需反向顺序复测，之后才能选择质量验证候选。

## 资源与故障处理

- GPU 模型串行、每个候选使用独立进程，释放完整 CUDA 上下文后再启动下一项。
- 保持分配显存不超过 9 GiB、进程 RSS 不超过 24 GiB、系统可用内存不少于 4 GiB 的门槛。超限或 CUDA OOM 写入拒绝报告，结束该进程，并停止该模型更大 batch 的尝试。
- 不自动缩小 batch、降低维度或改变词表；非资源类异常停止整个队列，保留日志。
- 运行前核对前序基线队列全部成功及已知训练进程退出。等待状态中若检测到前序失败或任务中断，停止而不是盲目继续。
- 该扫描不计算验证/测试效果、不保存可用于效果比较的训练检查点，也不自动选择最大 batch。不同 batch 的更新次数不同，因此资源报告不能替代学习率和训练质量评估。

## 入口与下一步

`run_batch_scan.py` 接受 `--after-study`、`--output-dir`、`--store`、`--content-project`、`--hist-cache`、`--content-checkpoint` 和 `--c6-config`，按顺序调用 `probe_batch_size.py`。输出目录须为新目录，状态和逐项日志可追踪。当前扫描配置预计需约 20–40 分钟，最终以实测为准。

可行候选反向复测后，按[联合评估协议](batch-and-hyperparameter-selection.md)对 batch 与 dense/sparse 学习率进行有限验证比较。当前全部主效果结果仍属于 batch=32 协议，不能将后续新协议混入原表。

## 加长复测与条件扩展

后续以相同 4,096 条热身和 262,144 条测量预算，先按 256、128 的反向顺序复测。若 256 相对 128 的吞吐提升至少 5%，且峰值分配显存低于 8.8 GiB，才尝试 512；1024 同样要求 512 相对 256 继续改善且有资源余量。这些阈值只用于控制探索成本，不是模型质量判定或最大 batch 的证明。所有探测继续受 9 GiB/24 GiB/4 GiB 门槛约束。

`run_batch_followup.py` 等首轮成功后串行执行上述步骤，逐项记录完成、超限和跳过原因。当前加长复测已启动，预计约 20–35 分钟；尚未选定新 batch。更大 batch 若资源不通过，不自动减小模型或更改数据来强行容纳。

模型训练数据是否足够仍是独立问题：扩容评估需结合低频/长历史分组的样本量与效果证据，而不是用更大 batch 代替更多训练数据。最终规模仍未冻结。
