# 阶段 9：基线整模型接入与资源准入

## 已完成的工程验证

四个本地适配基线已接入 `train_muse.py`：B0-short（只使用最近 50 条的公共注意力）、B1-hard-enhanced（同类目检索）、B2-soft-enhanced（共享商品与类目拼接向量余弦检索）、G-ID-item（共享商品 ID 余弦检索）。后三者保持与 R4 一致的增强 ESU；B0-short 不应称原始 DIN 完整复现。

新增模型继承现有主干与初始化，未改变原有 MUSEModel。内容检索参考变体的前向和各参数梯度与原模型逐项一致；seed 42 的 R4-L1000 检查点在验证集前 32 条回放误差为零。整套单元测试 24 项通过。该回放是代码迁移检查，不是完整验证重新评估。

B2 将商品与类目两个 embedding 拼接后归一化，与参考代码的检索空间一致。未知字段对应分量显式置零；只要商品或类目之一已知且向量非零即可作为候选。两者均未知时按已记录的回退策略处理。这一 OOV 策略属于本地适配。检索不反传，选中 ID 在 ESU 中重新查共享 embedding，使其通过 CTR 损失更新。

## 资源管理决策

1. 当前主对照保持 5% 数据、batch=32、16 维 ID embedding、原优化器与一轮训练，不通过持续降低 batch 换取更大数据规模。
2. 一次只运行一个 GPU 模型，四组任务串行；任一任务失败则停止后续任务。短探测的准入门槛为 PyTorch 分配显存不超过 9 GiB、进程 RSS 不超过 24 GiB、系统可用内存不少于 4 GiB；这些是保守工程门槛，不是硬件理论上限。新基线配置启用同阈值运行检查：首步及每 100 个训练步、每 100 个验证批次采样，超限记录故障并退出，不自动改 batch。采样不能保证捕获间隔内的瞬时峰值。
3. 扩容优先核算词表及 SparseAdam 状态，其次是 CPU 查表、I/O、吞吐和全部模型/种子总预算。降低维度、改词表映射或优化器均会改变协议，需要重新统一对照，不作为静默资源调整。
4. 先完成本轮必要基线，再依据实测决定更大子集是否值得。5% 继续作为候选主规模；不以最大数据量为优化目标，最终规模尚未冻结。
