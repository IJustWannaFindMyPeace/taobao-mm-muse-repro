# 阶段 12：批大小与学习率的训练质量筛选

> 文档性质：阶段记录／历史协议。本文中的规模、配置、验证结果及待办状态属于记录时点；当前结果以[主测试](final-test-results.md)、[补充测试](supplementary-test-results.md)和[覆盖说明](current-reproduction-status.md)为准。

## 目的与固定条件

资源扫描证明较大 batch 可提高吞吐，但不能证明训练质量保持不变。本阶段在固定 5% 数据上比较 R4 的 batch 256/512 与学习率，不扩大样本规模。每组 seed 42、L=1000、K=50、16 维 ID embedding、完整一轮训练，共 3,052,475 条训练曝光、768,773 条完整验证曝光。网络结构、初始化规则、样本置乱规则、优化器种类和 weight decay 不变。

一轮曝光预算相同，但 batch 256 与 512 分别约 11,924 和 5,962 次更新；原 batch 32 约 95,390 次。该差异是本轮要评估的训练协议影响，不将相同 epoch 误称相同更新预算。

网格包含当前学习率与参考学习率量级，分别改变两类参数的学习率，不按 batch 倍率盲目放大。优化器仍为本地既定配置，不能把某一学习率对称为完整论文训练设置。此小网格不是穷举搜索；若全部明显退化，先检查学习曲线与更新预算，不能自动宣布旧小批量最优或继续扩大数据。

完整机器可读协议见[配置清单](../configs/batch-quality-screen-protocol.json)，具体配置以 `tune-r4-b*` 命名。

## 资源和执行

队列单 GPU 串行，任一运行失败则停止后续任务。使用 9 GiB 提醒线、10.5 GiB 分配上限、CUDA 剩余显存至少 1 GiB，以及 RSS 24 GiB/系统可用内存 4 GiB 门槛。首步和每 100 训练步、每 100 验证批次检查；采样并非连续监测，不能保证捕获瞬时峰值。未改变已有 batch 32 运行的配置与报告。

新增报告记录验证及预测保存时间、训练开始后的端到端耗时、CUDA 采样最少剩余量，避免只按短探测吞吐估算总预算。预计 8 组约 3–5 小时，实际以全轮记录为准。队列已启动，尚无完整结果。

## 审计和候选确认

运行完成后逐项核验：完整训练行数和步数、配置快照、同源实现与数据摘要、完整验证源行/标签/用户对齐、保存预测重算指标，以及检查点重载。对比原 batch 32 时核对未变的模型依赖，明确训练入口新增资源监测与计时，不通过忽略摘要差异冒充相同代码。

以验证 GAUC 为主要筛选指标，同时展示 AUC、LogLoss、总耗时及资源。先保留每个 batch 的最佳学习率候选；并列时先比较较低 LogLoss，再按配置名排序保证可重复。明显的指标权衡单列，不能拿某项最高值替代全部指标。

候选还需在另一训练种子和伴随项目 C6 上确认，再决定共同主配置。这里复用验证集进行超参数选择，最佳点存在选择偏差；用户 bootstrap 不能作为独立确认，保留测试集不得参与选择。现有 batch 32 结果保留为旧协议证据，新主协议若确定须统一重跑关键对照。

最终数据规模尚未冻结；只有合理的训练配置和总预算明确后，再评估更大数据能否加强低频/长历史等关键证据。
